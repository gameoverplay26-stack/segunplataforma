Te propongo dos clases complementarias de 2 horas cada una: primero, **testing de integración para videojuegos**, y luego, **introducción a las plataformas de videojuegos y sus criterios de diseño**. De esta manera, los estudiantes aplican lo aprendido sobre pruebas unitarias y Jira en un contexto más amplio, y después relacionan el diseño del juego con la plataforma de destino.

# Clase 1: Testing de integración para videojuegos

**Duración:** 2 horas  
**Tema:** Pruebas de integración en proyectos de videojuegos  
**Modalidad:** Teórico-práctica  
**Herramientas sugeridas:** Unity, Unity Test Framework, Jira o herramienta similar, proyecto de juego previamente desarrollado.

## Objetivos

Al finalizar la clase, los estudiantes podrán:

- Diferenciar pruebas unitarias, de integración y funcionales.
- Identificar sistemas de un videojuego que deben probarse conjuntamente.
- Diseñar casos de prueba de integración.
- Ejecutar una prueba de integración sencilla en Unity.
- Registrar errores encontrados mediante un ticket en Jira.
- Analizar el impacto de un error en un flujo completo del juego.

## Contenidos

- Concepto de integración en videojuegos.
- Diferencias entre:
  - Pruebas unitarias.
  - Pruebas de integración.
  - Pruebas funcionales.
  - Pruebas de sistema.
- Ejemplos de integración:
  - Personaje + sistema de vida.
  - Personaje + inventario.
  - Enemigo + daño + puntuación.
  - Menú + cambio de escena.
  - Guardado + carga de partida.
  - Objetivos + sistema de recompensas.
- Pruebas con escenas y objetos reales.
- Dependencias entre sistemas.
- Datos de prueba y condiciones iniciales.
- Registro y seguimiento de errores.

---

## Desarrollo de la clase

### 1. Introducción y recuperación de conocimientos previos — 15 minutos

Comenzar con preguntas breves:

- ¿Qué verifica una prueba unitaria?
- ¿Qué ocurre si cada componente funciona por separado, pero falla cuando se conectan?
- ¿Qué diferencia hay entre probar un método y probar un flujo completo?
- ¿Qué información debe tener un ticket de bug?

Presentar un ejemplo:

> El sistema de inventario funciona correctamente en forma aislada. El sistema de recolección también funciona. Sin embargo, al recoger un objeto, este no aparece en el inventario.

Este caso permite introducir el concepto de prueba de integración.

---

### 2. Explicación teórica — 25 minutos

Presentar la siguiente comparación:

| Tipo de prueba | Qué verifica | Ejemplo |
| :--- | :--- | :--- |
| Unitaria | Una unidad de código aislada | El método `AgregarVida()` aumenta correctamente la vida |
| Integración | La comunicación entre dos o más sistemas | Recoger una poción y agregarla al inventario |
| Funcional | Una funcionalidad completa | Comprar, equipar y utilizar un objeto |
| De sistema | El juego completo en condiciones similares a las reales | Completar un nivel desde el inicio hasta el final |

Aclarar que una prueba de integración no necesariamente prueba todo el juego. Su objetivo es verificar que varios componentes funcionen correctamente en conjunto.

#### Ejemplos de flujos de integración

- El jugador recibe daño y la barra de vida se actualiza.
- El jugador derrota a un enemigo y recibe puntos.
- El jugador recoge una moneda y el contador se actualiza.
- El jugador completa un objetivo y se desbloquea una nueva escena.
- El jugador guarda la partida y luego puede recuperar su progreso.
- El jugador selecciona una opción en el menú y cambia correctamente de escena.

---

### 3. Análisis de un proyecto — 15 minutos

Dividir a los estudiantes en grupos pequeños.

Cada grupo debe analizar un proyecto de Unity y elegir un flujo que involucre al menos dos sistemas.

Algunas opciones:

1. Recolección de objetos e inventario.
2. Daño del jugador y actualización de la interfaz.
3. Muerte de un enemigo y aumento de puntuación.
4. Finalización de un nivel y desbloqueo del siguiente.
5. Guardado y carga de partida.

Cada grupo debe responder:

- ¿Qué sistemas participan?
- ¿Qué evento inicia el flujo?
- ¿Cuál debería ser el resultado esperado?
- ¿Qué podría fallar?
- ¿Qué datos necesitan para realizar la prueba?

---

## Actividad práctica principal: diseñar y ejecutar una prueba de integración

**Duración:** 45 minutos

### Consigna

Cada grupo deberá diseñar y ejecutar al menos una prueba de integración sobre un proyecto de Unity.

### Ejemplo de actividad: daño al jugador

El flujo puede ser:

1. El jugador entra en contacto con un enemigo.
2. El enemigo genera daño.
3. El jugador reduce su cantidad de vida.
4. La interfaz actualiza la barra de vida.
5. Si la vida llega a cero, se activa el estado de derrota.

### Caso de prueba

| Campo | Ejemplo |
| :--- | :--- |
| ID | INT-001 |
| Nombre | El jugador recibe daño y actualiza la barra de vida |
| Precondiciones | El jugador comienza con 100 puntos de vida |
| Datos de prueba | Daño del enemigo: 25 puntos |
| Pasos | 1. Iniciar la escena. 2. Colocar al jugador frente al enemigo. 3. Provocar la colisión. 4. Observar la vida y la interfaz |
| Resultado esperado | La vida disminuye a 75 y la barra se actualiza |
| Resultado obtenido | Completar durante la ejecución |
| Estado | Aprobado o Fallido |

### Posible implementación en Unity

Los estudiantes pueden utilizar:

- Una escena de prueba.
- Un jugador.
- Un objeto que represente al enemigo.
- Un componente de vida.
- Un componente de daño.
- Un elemento de UI para mostrar la vida.
- El Unity Test Framework cuando sea posible.

En caso de que el proyecto no permita automatizar toda la prueba, pueden realizar una prueba de integración manual documentada. Es importante explicar que no todas las pruebas de integración deben ser necesariamente automatizadas.

---

### 4. Registro del bug en Jira — 15 minutos

Si la prueba falla, los estudiantes deben crear un ticket.

El ticket debe contener:

- Título claro y específico.
- Descripción del problema.
- Pasos para reproducirlo.
- Resultado esperado.
- Resultado actual.
- Evidencia, como captura de pantalla o video.
- Prioridad.
- Severidad.
- Entorno de prueba.
- Persona asignada.

#### Ejemplo de ticket

**Título:** La barra de vida no se actualiza después de recibir daño

**Descripción:**  
Al recibir daño de un enemigo, el valor interno de vida del jugador disminuye, pero la barra de vida permanece visualmente en 100%.

**Pasos para reproducir:**

1. Abrir la escena `Nivel01`.
2. Iniciar el juego.
3. Colocar al jugador en contacto con el enemigo.
4. Observar la barra de vida.

**Resultado esperado:**  
La vida y la barra deben disminuir de 100% a 75%.

**Resultado actual:**  
La vida interna disminuye, pero la barra continúa mostrando 100%.

**Severidad:** Media  
**Prioridad:** Alta  
**Evidencia:** Captura o video de la ejecución.

---

### 5. Puesta en común — 10 minutos

Cada grupo presenta:

- El flujo seleccionado.
- Los sistemas involucrados.
- El caso de prueba.
- El resultado obtenido.
- El ticket creado, si encontraron un error.

---

### 6. Cierre y evaluación — 10 minutos

Realizar una breve actividad individual:

> Explicar con un ejemplo propio la diferencia entre una prueba unitaria y una prueba de integración.

También pueden responder:

- ¿Qué sistema fue más difícil de probar?
- ¿Qué dependencia generó mayor riesgo?
- ¿Qué información fue necesaria para reproducir el error?

## Producto final de la clase

Cada grupo debe entregar:

1. Un diagrama simple del flujo probado.
2. Un caso de prueba de integración.
3. La evidencia de ejecución.
4. Un ticket en Jira si la prueba detectó un error.
5. Una breve conclusión sobre el resultado.

## Criterios de evaluación

| Criterio | Porcentaje |
| :--- | :--- |
| Identificación de los sistemas involucrados | 20% |
| Diseño del caso de prueba | 25% |
| Ejecución y registro de resultados | 25% |
| Calidad del ticket de Jira | 20% |
| Presentación y reflexión final | 10% |

# Clase 2: Introducción a las plataformas de videojuegos

**Duración:** 2 horas  
**Tema:** Tipos de plataformas y adaptación del diseño  
**Modalidad:** Teórico-práctica  
**Herramientas sugeridas:** Unity, fichas de análisis, capturas o videos de videojuegos.

## Objetivos

Al finalizar la clase, los estudiantes podrán:

- Reconocer las principales plataformas de videojuegos.
- Comparar sus características técnicas y de uso.
- Identificar cómo la plataforma condiciona el diseño del juego.
- Analizar controles, interfaz, rendimiento y experiencia de usuario.
- Proponer adaptaciones de un mismo juego para distintas plataformas.
- Elaborar una ficha de diseño orientada a una plataforma específica.

## Contenidos

- PC.
- Consolas.
- Dispositivos móviles.
- Navegadores y juegos web.
- Realidad virtual y realidad aumentada.
- Diferencias entre plataformas:
  - Dispositivos de entrada.
  - Tamaño de pantalla.
  - Rendimiento.
  - Resolución.
  - Memoria.
  - Conectividad.
  - Modelo de distribución.
  - Tiempo de juego.
  - Interfaz de usuario.
  - Accesibilidad.
- Portabilidad y multiplataforma.
- Concepto de diseño orientado a plataforma.

---

## Desarrollo de la clase

### 1. Actividad inicial — 10 minutos

Mostrar imágenes o videos breves de juegos desarrollados para distintas plataformas.

Preguntar:

- ¿Cómo saben para qué plataforma fue diseñado cada juego?
- ¿Qué diferencias observan en los controles?
- ¿Qué elementos de la interfaz cambiarían?
- ¿Un mismo juego puede funcionar igual en todas las plataformas?

Registrar las respuestas en el pizarrón.

---

### 2. Explicación teórica — 30 minutos

### PC

Características habituales:

- Gran variedad de configuraciones de hardware.
- Uso de teclado y mouse, aunque también puede utilizarse joystick.
- Diferentes resoluciones y relaciones de aspecto.
- Posibilidad de modificar gráficos y rendimiento.
- Mayor flexibilidad para controles y configuración.

Aspectos de diseño:

- Permitir reasignar teclas.
- Incorporar distintos niveles gráficos.
- Adaptar la interfaz a múltiples resoluciones.
- Considerar el uso de mouse, teclado y joystick.
- Ofrecer opciones de accesibilidad.

### Consolas

Características habituales:

- Hardware más uniforme.
- Uso principal de joystick.
- Interacción desde una distancia mayor respecto de la pantalla.
- Experiencia más orientada a jugar desde una pantalla grande.
- Necesidad de cumplir requisitos de publicación y certificación.

Aspectos de diseño:

- Menús navegables con joystick.
- Botones y textos fácilmente legibles.
- Vibración y retroalimentación háptica.
- Guardado y pausa adaptados al uso de consola.
- Evitar depender exclusivamente del mouse o del teclado.

### Dispositivos móviles

Características habituales:

- Pantallas táctiles.
- Diferentes tamaños y resoluciones.
- Uso en sesiones breves o intermitentes.
- Recursos de hardware variables.
- Posible uso de sensores, cámara, GPS o conectividad móvil.

Aspectos de diseño:

- Botones táctiles suficientemente grandes.
- Interfaz clara y simple.
- Control mediante gestos.
- Bajo consumo de batería.
- Carga rápida y posibilidad de pausar fácilmente.
- Adaptación a orientación vertical u horizontal.

### Juegos web

Características habituales:

- Acceso desde un navegador.
- No requieren instalación tradicional.
- Variación en conexión y rendimiento.
- Posible uso de teclado, mouse o controles táctiles.

Aspectos de diseño:

- Tiempo de carga reducido.
- Interfaz directa.
- Compatibilidad con distintos navegadores.
- Tolerancia a interrupciones de conexión.
- Resolución adaptable.

### Realidad virtual

Características habituales:

- Uso de visor y controles de movimiento.
- Necesidad de mantener una alta fluidez.
- Interacción espacial.
- Riesgo de incomodidad o mareo.

Aspectos de diseño:

- Movimiento controlado.
- Evitar cambios bruscos de cámara.
- Interacciones físicas claras.
- Espacios seguros y accesibles.
- Alto cuidado del rendimiento.

# Actividad práctica principal: adaptar un juego a una plataforma

**Duración:** 45 minutos

## Consigna

Presentar a los estudiantes un juego base sencillo, por ejemplo:

- Juego de plataformas 2D.
- Juego de disparos.
- Juego de puzzles.
- Juego de carrera.
- Juego de aventura con inventario.

Cada grupo deberá imaginar que el juego será publicado en una plataforma específica:

- PC.
- Consola.
- Móvil.
- Navegador.
- Realidad virtual.

Deberán modificar conceptualmente el diseño del juego teniendo en cuenta:

1. Tipo de control.
2. Interfaz.
3. Duración de las partidas.
4. Dificultad.
5. Rendimiento.
6. Resolución y tamaño de pantalla.
7. Accesibilidad.
8. Forma de guardado.
9. Modelo de distribución.
10. Pruebas que deberían realizarse.

### Ejemplo: adaptar un juego de plataformas a móvil

**Control original:** teclado con las flechas y barra espaciadora.  
**Adaptación:** botones táctiles o controles mediante gestos.

**Cambios necesarios:**

- Aumentar el tamaño de los botones.
- Evitar acciones que requieran demasiada precisión.
- Incorporar pausa rápida.
- Reducir la duración de cada nivel.
- Optimizar el consumo de batería.
- Probar diferentes tamaños de pantalla.
- Verificar que la interfaz no quede tapada por los dedos.
- Probar el juego con distintas relaciones de aspecto.

### Ejemplo: adaptar el mismo juego a consola

- Reemplazar las teclas por botones del joystick.
- Permitir navegar todos los menús con el control.
- Incorporar vibración opcional.
- Ajustar el tamaño de los textos para jugar a distancia.
- Probar diferentes configuraciones de joystick.
- Evitar que una acción importante dependa del mouse.

---

## 4. Relación con testing — 10 minutos

Cada grupo deberá elaborar una lista de pruebas para su plataforma.

### Ejemplo de pruebas para un juego móvil

- El juego se adapta a distintas resoluciones.
- Los botones táctiles responden correctamente.
- El jugador puede pausar durante una llamada o interrupción.
- La interfaz funciona en orientación vertical y horizontal.
- El rendimiento es estable en dispositivos de distintas capacidades.
- La batería no se consume excesivamente.
- El texto es legible en pantallas pequeñas.

### Ejemplo de pruebas para consola

- Todos los menús pueden utilizarse con joystick.
- El juego reconoce correctamente la desconexión del control.
- El texto se lee desde una distancia normal.
- La vibración se activa en los momentos correspondientes.
- El juego guarda correctamente el progreso.
- El jugador puede reiniciar o pausar sin utilizar teclado.

---

> La plataforma no es solamente el lugar donde se ejecuta un videojuego. También condiciona sus controles, su interfaz, el ritmo de juego, la accesibilidad, el rendimiento y las pruebas necesarias.

# Secuencia recomendada

La secuencia más conveniente sería:

1. **Clase 1: Testing de integración**
   - Continúa directamente con las pruebas unitarias y Jira.
   - Permite trabajar con sistemas ya conocidos.
   - Ayuda a comprender cómo se prueban flujos completos.

2. **Clase 2: Plataformas de videojuegos**
   - Amplía el análisis hacia el diseño.
   - Permite entender que cada plataforma requiere diferentes pruebas.
   - Prepara el camino para temas como multiplataforma, optimización y accesibilidad.

Como actividad final integradora, se puede pedir a los estudiantes que tomen la prueba de integración desarrollada en la primera clase y respondan:

> ¿Cómo cambiaría esta prueba si el juego estuviera diseñado para PC, consola o móvil?

Por ejemplo, no se probaría de la misma manera un menú controlado con mouse en PC que un menú utilizado mediante pantalla táctil o joystick.
